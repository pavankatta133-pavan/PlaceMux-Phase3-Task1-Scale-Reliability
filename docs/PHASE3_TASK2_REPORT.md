# PlaceMux Phase 3 Task 2
# Sprint A - Scale & Reliability
# Observability Deep-Dive, SLOs & Error Budgets

## 1. Objective

The objective of this task was to establish an observability and reliability
foundation for the PlaceMux AI recommendation service.

The implementation focuses on inference SLOs, monitoring, alerting,
error budgets, and failure-path testing.

## 2. SLO Definition

The following engineering SLO targets were defined:

| Metric | Target |
|---|---:|
| P95 inference latency | <= 500 ms |
| Availability | >= 99% |
| Minimum prediction quality score | >= 50 |
| Latency compliance | >= 95% |
| Quality compliance | >= 95% |

These thresholds provide a measurable baseline for monitoring the
recommendation service.

## 3. Observability Metrics

The monitoring system uses the existing prediction logs generated by
the Phase 3 Task 1 implementation.

The following metrics are calculated:

- Total requests
- Successful requests
- Availability percentage
- Average latency
- P95 latency
- Average prediction score
- Minimum prediction score
- Maximum prediction score
- Number of unique prediction scores

## 4. Monitoring

The observability monitor reads:

`post_launch_health/logs/prediction_logs.csv`

and generates:

`observability/reports/slo_report.json`

This provides a machine-readable summary of the current SLO status.

## 5. Alerting

An alert manager was implemented to detect reliability and model-health
problems.

The system checks for:

- High latency
- Critical latency
- Availability breaches
- Low prediction quality
- Low score diversity
- Degenerate/constant prediction scores

Alerts are written to:

`observability/reports/alert_report.json`

and:

`observability/logs/observability_alerts.json`

## 6. Synthetic Breach Testing

Synthetic testing was performed without permanently changing the original
prediction data.

A latency breach was simulated by increasing prediction latency to
750 ms while the configured critical threshold was 500 ms.

A degenerate-score scenario was also simulated by making all predictions
return the same score.

The monitoring system detected the abnormal behaviour and generated
corresponding alerts.

After testing, the original prediction log was restored.

## 7. Error Budget

An error-budget calculation was implemented based on the configured SLOs.

The system calculates remaining reliability budget for:

- Availability
- Latency
- Prediction quality

The result is stored in:

`observability/reports/error_budget_report.json`

The error budget provides a way to decide whether additional changes can
be safely introduced or whether reliability improvements should take
priority.

## 8. Failure-Path Testing

A failure scenario was deliberately introduced to verify that the
monitoring system responds to service degradation.

The test generated a failed prediction with high latency.

The system detected:

- Availability degradation
- Latency degradation
- SLO breach
- Corresponding alerts

The original prediction logs were restored after the test.
